# 容器部署第一步：本机 Compose 验证

本目录先把当前应用装进 Linux 容器，本机验证服务可组合运行。它不替代下一步的云端剪映导出包/导入工具，也不提供公网 TLS。

## 文件

- `deploy/server.Dockerfile`：API、Worker、Beat 共用的 Python 镜像，包含后端依赖和 FFmpeg。
- `deploy/web.Dockerfile`：多阶段构建前端，并用 Nginx 提供静态文件。
- `deploy/nginx.conf`：SPA 回退、API/SSE 代理和上传限制。
- `deploy/compose.yaml`：PostgreSQL、Redis、API、Worker、单实例 Beat、Web 六个服务；数据使用 Docker volumes。
- `deploy/.env.docker.example`：容器环境变量模板。
- `.dockerignore`：排除密钥、数据库、依赖、构建产物和恢复备份。

## 本机前置

安装并启动 Docker Desktop，启用 Linux containers。仓库当前使用 Windows，本机容器运行的是 Linux 环境。确认：

```powershell
docker version
docker compose version
```

## 启动

从项目根目录执行，复制模板并编辑 `deploy/.env.docker`：

```powershell
Copy-Item deploy/.env.docker.example deploy/.env.docker
```

设置两个足够长的 URL-safe 随机值作为 `POSTGRES_PASSWORD` 和 `REDIS_PASSWORD`；不要使用 `@`, `:`, `/`, `#` 等 URL 保留符号。模板默认 `LINGZHU_DEMO_MODE=true` 且模型/OSS 密钥为空，Compose 仅读取 `LINGZHU_*` 前缀的凭据，避免意外继承宿主机根 `.env` 或同名环境变量中的 API Key。想显式启用真实模型时，填写 `LINGZHU_DEEPSEEK_API_KEY`、`LINGZHU_DASHSCOPE_API_KEY` 或 `LINGZHU_ARK_API_KEY` 并将 `LINGZHU_DEMO_MODE=false`。如果 OSS 尚未准备好，可留空，让文件存到共享的 `app_data` volume。本机访问默认 Origin 为 `http://localhost:8080`；云端将 `CORS_ORIGINS` 改为实际 HTTPS Origin，并把 `AUTH_COOKIE_SECURE=true`。

构建并启动：

```powershell
docker compose --env-file deploy/.env.docker -f deploy/compose.yaml up --build -d
docker compose --env-file deploy/.env.docker -f deploy/compose.yaml ps
docker compose --env-file deploy/.env.docker -f deploy/compose.yaml logs -f api worker beat
```

浏览器打开 `http://localhost:8080`，健康检查为 `http://localhost:8080/api/v1/health`。Beat 独立运行且只能保留一个副本。停止服务使用 `docker compose --env-file deploy/.env.docker -f deploy/compose.yaml down`；不要加 `-v`，否则会删除数据库和 Redis 持久卷。

## 容器间网络

- API、Worker、Beat 共用一个构建镜像和同一份业务配置。
- Postgres、Redis 不发布宿主机端口，仅在 Compose 网络中可达。
- API 启动时现有 lifespan 会建表并运行本地 schema 对齐逻辑；Worker 和 Beat 等 API 健康后才启动。
- API lifespan 同时初始化 LangGraph PostgreSQL checkpoint migrations/indexes；请求中只打开已就绪的检查点，不再在首条对话里执行并发建索引。
- Web 只将 `127.0.0.1:WEB_PORT` 发布到宿主机；Nginx 代理 `/api/` 并关闭 SSE buffering。
- Postgres、Redis 与 `/app/data` 使用持久化 volumes；Compose 删除容器不会删除数据。

## 本步骤的验收

1. 六个服务状态正常，API 与 Web healthcheck 通过。
2. 可以注册、登录、上传文档、执行改写、进入 Agent SSE 流程。
3. Worker 收到任务，Beat 每 10 秒投递 Outbox 扫描、每 30 秒运行恢复扫描。
4. 停止并重新启动容器后，用户、任务和文件仍在。
5. 有 OSS 时用私有 Bucket 上传和读取；无 OSS 时文件保存在 `app_data`，这是单机测试回退，不是多实例云端共享方案。

## 当前本机冒烟结果

已在 Docker Desktop Linux Engine 上完成 `docker compose build` 和 `up -d`。初次启动发现镜像曾把 `apps/server/app` 扁平复制到 `/app/app`，与 `core/config.py` 计算仓库根目录的假设不符；后端报 `IndexError`，健康检查失败。Dockerfile 已改为保留 `/app/apps/server/app` 结构，数据目录挂载同步到 `/app/apps/server/data`，重建后正常启动。

本次实际验证：PostgreSQL/Redis healthy，API healthy，Web healthy；Worker 与 Beat 均处于运行状态；`http://localhost:8080/` 返回 200，`/api/v1/health` 返回 `status=ok`。前端独立 `npm.cmd run build` 也通过。LangGraph 检查点现于 API 启动期完成迁移初始化；首条对话的只读图状态查询已实测返回空状态。一次被中断的初始化留下无效索引后，启动修复会清理并重建索引。

当前 Compose 使用模板中的非生产占位凭据，仅用于本机容器冒烟。部署或在其他机器长期运行前，应创建被 gitignore 排除的 `deploy/.env.docker`，设置独立随机 URL-safe 密码、正式 HTTPS Origin、Cookie Secure=true，并只填写明确选择的服务密钥。不要把示例占位密码用于公网部署。

## 未包含在此步骤

- 宿主机 HTTPS 反向代理、域名和防火墙规则：应在云主机 TLS 入口完成；Compose Web 仅绑定回环地址。
- 云端剪映导出包和 Windows 本机导入工具。
- 数据库定期备份、恢复演练、Alembic 迁移和多实例扩容。
- Docker Daemon/BuildKit 尚未在当前执行环境验证；构建失败需在安装 Docker Desktop 的机器运行上述命令，并按服务日志排查。
