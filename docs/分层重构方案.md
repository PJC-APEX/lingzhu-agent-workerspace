# lingzhu-agent 分层重构方案

> 本文件是 `docs/路由拆分清单.md` 的上位方案。
> 清单只解决 `routes.py` 一个文件，本方案解决**整个后端的层次归属**。
> 两者关系：**先执行本方案的 P0，再执行清单的步骤 2–7。**

---

## 零、一句话目标

让每个文件只回答一个问题：「你负责什么？」

- `api/` 负责收请求、回响应
- `application/` 负责「这件事该怎么办」
- `services/` 负责「这个能力怎么实现」
- `infrastructure/` 负责「怎么连上、怎么存取、怎么传输」
- `domain/` 负责「数据长什么样」

---

## 一、五层的定义与判断规则

### 判断口诀

| 层 | 能出现 | 绝对不能出现 |
|---|---|---|
| `api/` | 路径、参数、状态码、SSE 编码 | `db.query`、`db.commit`、业务 if/else |
| `application/` | `db.query`、事务、409/422 判断、`HTTPException`、`user_id` | FastAPI 的 `Request`/`Response`、路由装饰器 |
| `services/` | 算法、外部 API 调用、返回纯数据 | `db`、`user_id`、`HTTPException` |
| `infrastructure/` | 引擎、连接池、Redis client、文件 IO | `HTTPException`、业务判断、`from app.main import` |
| `domain/` | SQLAlchemy 模型、纯数据类 | 任何 IO、任何三方 SDK |

### 最实用的三条自检

1. **`services/` 里出现了 `user_id` 或 `HTTPException` → 放错了**
2. **`infrastructure/` 里出现了 `from app.main` 或 `from app.api` → 依赖戳穿了**
3. **`api/` 里出现了 `db.commit()` → 业务没下沉**

| **P2** | 新增 `application/` + `repositories/`，业务下沉 | 5–7 天 | 中高 | api 层零业务，services 层零 user_id | 主体工程，分批 PR |
| **P3** | 图节点与 worker 依赖掰正 | 2–3 天 | 中 | 依赖单向，无环 | P2 完成后 |
| **P4** | Alembic / 删废代码 / 前端拆分 / CI | 3–4 天 | 低 | 可回滚、可审计、有护栏 | 最后收尾 |

**总计约 15–21 个工作日**，拆成 5 个可独立验收的阶段。

### 关键原则

1. **不重写逻辑，只搬位置。** 你写好的对齐/生图/分镜/剪映一行都不用改，只是换个地方放。
2. **每阶段可停。** P0 做完就能长期停（地基已正）；P1 做完就能停（文件已拆清）；P2 做完就是标准分层。
3. **搬移和改逻辑绝不混在一次提交里。** 否则出问题无法判断是哪一类改动导致。
4. **`docs/路由拆分清单.md` 不要重做。** 它的 37 个端点归属分析是对的，只是行号基于 1695 行版本（现已 1770 行），
   按**端点路径**定位，不要按行号。P1 阶段直接照它执行。

## 六、如果时间有限，只做这三件事

按性价比排序，做完这三件能解决 80% 的痛点：

1. **P0-2 删掉 `database.py` 里的 `from app.main import app`** —— 一小时，消除最严重的依赖倒挂
2. **P1-1 + P1-2 拆出 `health.py` / `system.py` / `job.py`** —— 半天，验证拆法可行，建立信心
3. **P2-2 document 模块完整下沉** —— 两天，做出一个标准样板，后面 7 个模块照着抄

做完之后，`routes.py` 里剩下的部分即使还没拆，你也已经知道「正确长什么样」了。
